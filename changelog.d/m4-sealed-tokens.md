**Breaking (storage): access tokens are now sealed at rest by `EncryptedStorage` (ADR-011, slice 2 of 4).** `store_token`, `get_token`, `get_token_by_access_token`, `update_token`, `delete_token`, `list_user_tokens` and the bulk token methods keep each token as one encrypted record in the backend's key-value space, indexed by keyed hashes, so no access token, refresh token, user id or token id appears in a stored key or value. Key names beginning `tok:`, `tokat:` and `tokuser:` are reserved: the key-value methods refuse them and `list_kv_keys` omits them. A token stored before this release is read through when `allow_plaintext_reads` is true (it is sealed and the old row deleted); with it false, an old row is unreachable by lookup but is still revoked and deleted by `update_token` and `delete_token`. The typed token tables of SQL backends are no longer written while encryption is on. Sessions are not sealed yet (slice 3). An `EncryptedStorage` over a backend that cannot list KV keys or report TTLs now returns an error from the token methods; the storage factory refuses such a backend at construction.
