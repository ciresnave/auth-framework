**Breaking: `GnapIssuedToken` gains `manage_token` and `label`, is `#[non_exhaustive]`, and `GnapTokenStore` gains `get_by_manage_token`.** A token now carries the client's `label` (echoed at issue and again on rotation, RFC 9635 3.2.1 and 3.3) and a management secret kept apart from the access-token value. Migration: build tokens with `GnapIssuedToken::new(..)` plus `with_key`/`with_manage_token`/`with_label` instead of a struct literal, and implement `get_by_manage_token` on a custom `GnapTokenStore` (return the stored token whose `manage_token` equals the argument). Records stored before this change load unchanged (both fields default to `None`) and are still managed by their value. Evidence: `an_old_record_without_the_new_fields_still_loads`, `a_token_is_found_by_its_manage_token`, `rotation_echoes_the_label` in `gnap_store.rs`/`gnap.rs`; the `compile_fail` doctest on `GnapIssuedToken` shows the struct literal no longer compiles outside the crate.

**Breaking: the `manage` URI is now per token, `<grant endpoint>/token/<manage secret>` (RFC 9635 3.2.1).** `GnapAsHttp` routes `POST` (rotate) and `DELETE` (revoke) there; the DPoP/httpsig/JWS proof is bound to that full URI, an unknown secret is `404`, and a secret answers only for the token it names (or, within the rotation-retry window, the value it replaced). A rotation keeps the secret. Migration: clients must follow the `manage` they are given rather than building `<grant endpoint>/token`, and a proof for a managed token must name the per-token URL; the shared `<grant endpoint>/token` still serves tokens stored without a secret. Evidence: `a_token_is_issued_its_own_manage_uri_and_rotated_and_revoked_there`, `a_manage_uri_does_not_manage_another_tokens_value`, `an_unknown_manage_secret_is_404`, `a_retried_rotation_at_the_manage_uri_replays_the_answer` in `gnap_as_http.rs`.
