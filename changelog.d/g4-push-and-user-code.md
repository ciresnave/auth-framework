`GnapService::push_interaction` delivers the `push` callback of an approved transaction (RFC 9635 4.2.2, G4 slice 2). The host is resolved at delivery, the push is refused if **any** resolved address is loopback, private, link-local, metadata, shared or documentation range (11.34, no DNS-rebinding window), and the connection goes to the address that was checked, with no redirect followed and a timeout. New module `gnap_push` with `PushResolver`/`PushSender` traits, `SystemPushResolver` and `ReqwestPushSender` defaults and a typed `PushError`. Evidence: nine unit tests and four service tests; five mutations (the any-blocked check, the open-time guard, redirects, the pin, the approved-state check) each fail a test. `GnapService::transaction_for_user_code(typed, caller)` finds the pending transaction a person's typed user code belongs to (RFC 9635 3.3.3, G4 slice 3): case- and hyphen-insensitive, constant-time, one refusal for a wrong, malformed, expired or already-decided code, and five wrong codes in five minutes lock that caller out (the right code too). New `GnapTransactionStore::find_by_user_code` with a default implementation, so existing stores keep compiling. The lockout is per process and keyed by the caller the integrator passes. Evidence: six tests; three mutations (the lockout check, the expiry check, clearing the count on success) each fail a test. `GnapService::with_user_code_uri(uri)` (G4 slice 4) makes a `user_code_uri` start answer `{code, uri}` with the transaction's one user code; the URI must be absolute http(s) with no query or fragment, and without it the mode is not offered. Evidence: three tests; one mutation (emitting `user_code` unasked) fails a test.
