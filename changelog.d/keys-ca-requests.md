**A certificate authority can now certify a generated key, and a client's CSR is checked for proof of possession first.** `keys::certificate_request_for_key(key, &CertSubject, profile, requester)` builds the `CertificateRequest` that `X509CertificateManager::sign_certificate_request` takes, for a key the caller holds. `keys::certificate_request_from_csr(csr_pem, profile, requester)` does it for a PKCS#10 request received from someone else, **after verifying the request's signature**: `sign_certificate_request` takes a bare public key and checks no proof that the requester holds the private key, so a request whose signature does not verify (including one altered in transit) is now refused. Only the common name, the DNS names and the public key are taken; a request with an IP, e-mail or URI name, no common name or more than one is refused instead of partly honoured. The authority still applies its own profile, name and key policy and the caller must still authenticate and authorise the requester. No new dependency. Evidence: four new `keys::cert` tests that issue real certificates from a throwaway CA and check they certify the key and publish through `x5c`, three shown red by skipping the signature check, dropping non-DNS names and dropping DNS names.
