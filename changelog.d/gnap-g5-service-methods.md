**Breaking: GNAP polling enforces `wait`, and the client can modify or cancel a pending grant (ROADMAP G5, RFC 9635 sections 5.2-5.4); two fields renamed (SEC-012, #463).** `GnapService` gains `with_poll_wait_secs(n)` (default 5, 0 = off), `modify_transaction_with_proof` (PATCH: a pending transaction only, no `client` or `interact`) and `delete_transaction_with_proof` (DELETE: the client cancels its grant). A poll before `wait` has elapsed is refused with `TOO_FAST`, keeps the continuation token and restarts the clock; `GnapTransaction` gains `last_poll_at`, so literals of it must add the field, and callers that poll faster than 5 seconds must now wait or set `with_poll_wait_secs(0)`. Renamed with their wire names kept: `GnapTransactionRequest.access_token` is now `access_token_request` and `ServiceProviderConfig.change_password` is now `change_password_flag`; `AcmeChallenge.token` carries its `// sec012: public` marker. The HTTP routes for 429 `too_fast`, PATCH and DELETE are the surface lane's. Evidence: 271 lib tests match `gnap` with the CI feature set (6 new), `gnap_conformance` and `gnap_rs_conformance` pass, two tests pin the renamed fields' wire names, and CI clippy and `cargo +stable fmt --check` are clean. Also: **the admin binary now reads the configuration it is given (#442, M12).** `--config` and `--env-prefix` were accepted but ignored, so every run used the built-in defaults with an empty in-memory store while printing that the file was loaded; a `--config` path that is missing or unreadable is now an error, and with no `--config` the binary reads `config/auth-framework.toml` if it exists and otherwise says on stderr that it uses the built-in defaults (`auth_framework::admin::load_settings`; cherry-picked from e3d43ccf). Evidence: two binary tests fail on the old code (it printed "Configuration loaded" for a file that does not exist) and pass with the fix. Also: **`scripts/install.sh` and `scripts/install.ps1` requested `authframework-<tag>-<target>` archives that no release has, so both failed with a 404.** They now request what the release publishes (`auth-framework-<os>-<arch>[-musl].tar.gz` and `auth-framework-windows-x86_64.zip`, plus the `auth-framework-admin-` archives), verify the `.sha256` on Linux and macOS, and install `auth-framework` and `auth-framework-admin` (the old `authframework-server` and `authframework-cli` names never existed). Checked against release v0.6.0-rc217: the asset names, the checksum format and the archive layout match, and the old name returns 404; the scripts have not been run end to end, and there is no Windows ARM64 asset. Also: **`sqlx` 0.9.0 -> 0.9.1 and `libsqlite3-sys` 0.37.0 -> 0.40.0 (RUSTSEC-2026-0459, bundled SQLite CVE-2026-119375, fixed in 0.39.0).** sqlx 0.9.1 widens the cap to `<0.41` (transact-rs/sqlx#4502), so the lockfile now carries the fixed SQLite and the ignore is removed from `deny.toml` and `.cargo/audit.toml`; the manifest now requires `sqlx` 0.9.1 and, under `sqlite-storage` and `persistant-storage`, `libsqlite3-sys` `>=0.39, <0.41` (also in `auth-storage-sqlite`), so a consumer with an older lockfile cannot keep the vulnerable SQLite when it updates; no API change.
