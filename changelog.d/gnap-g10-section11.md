`section_11_16_only_the_push_delivery_makes_outbound_http` (`tests/gnap_section11_outbound.rs`) fails if any GNAP module other than `gnap_push.rs` names an HTTP client (RFC 9635 section 11.16: a client's `logo_uri` is never fetched); ROADMAP G10 is Done, with the section 11 items that are advice or have nothing to test named in the gap doc. The conformance suite `tests/conformance/gnap/vectors.json` is version 7 with five RFC 9635 Appendix B vectors: B.2 secondary device (`redirect` and `user_code` start, no finish, poll without a reference; the RFC's B.2 example writes `user_code` as an object while 3.3.3 says a string, and the AS follows the text) and B.5 B.4 with a malformed-user control (a `user` hint is read and checked; the AS issues at once under an allow-all policy, async approval is the deployer's policy), and B.5 (OAuth scopes as access strings: the `bearer` flag is refused as this AS issues key-bound tokens only, the same request without it is served). Also: `hash_method` `sha3-256` and `sha3-512` are computed (RFC 9635 4.2.3; new dependency `sha3` 0.12.0 from crates.io, rust-version 1.85; the RFC's own sha3-512 example is vector `hash-rfc-example-sha3-512`, suite version 8), and the service now raises key-material refusals as typed errors (`From<GnapError> for AuthError`; a malformed key, certificate or JWK is `invalid_request`, a failed client-key signature check is `invalid_client`): the AS answers with that code and its description (status 400, or 401 with `WWW-Authenticate: GNAP` for `invalid_client`) instead of the generic wording.
